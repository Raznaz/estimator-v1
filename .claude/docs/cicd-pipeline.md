# Что происходит при push и merge — пошагово

Учебная справка по пайплайну проекта. Файлы, о которых речь:
`.github/workflows/ci.yml`, `.github/workflows/deploy.yml`, `docker-compose.prod.yml`.
Чек-лист внедрения — `.claude/plans/cicd-checklist.md`.

---

## Шаг 1. `git push` в обычную ветку → **ничего не запускается**

Триггеры `ci.yml`:

```yaml
on:
  pull_request:
  push:
    branches: [main]
```

Push в `feat/...` под них не подходит. Сделано намеренно: пока «сохраняешься»
в свою ветку, раннеры не тратятся.

---

## Шаг 2. Открыл Pull Request → запускается `ci.yml`

В PR появляется проверка «Линт, типы, тесты, сборка». Раннер — чистая
виртуалка Ubuntu, создаётся с нуля каждый раз.

| Шаг | Что делает | ~Время |
|---|---|---|
| `checkout` | клонирует ветку | 5 сек |
| `setup-node` | Node 22 + кэш npm | 5–20 сек |
| `npm ci` | зависимости строго по `package-lock.json` | 30–60 сек |
| `prisma generate` | генерирует Prisma Client из схемы | 5 сек |
| `npm run lint` | ESLint по backend и frontend | 15 сек |
| `npm run typecheck` | `tsc --noEmit` в обоих пакетах | 20 сек |
| `npm run test` | 27 Jest-тестов | 5 сек |
| `npm run build` | `nest build` + `next build` | 40 сек |

Итого **2–3 минуты**.

Важное:

- **Шаги последовательные, падают на первом провале.** Сломался typecheck →
  тесты и сборка не запускаются вообще.
- **`prisma generate` обязателен** перед проверками: Prisma Client не лежит
  в репозитории, он генерируется из схемы.
- **Push исправления перезапускает CI**, а `concurrency` отменяет предыдущий
  незавершённый прогон.

Упало → красный крестик → «Details» → лог того шага с той же ошибкой,
что была бы в локальном терминале.

---

## Шаг 3. Нажал «Merge» → запускаются **два workflow одновременно**

### 3а. `ci.yml` ещё раз, теперь на `main`

Не избыточность: `main` мог уйти вперёд, пока PR висел, и получившаяся
комбинация кода никем не проверялась.

### 3б. `deploy.yml`, job `build`

1. Логин в GHCR по автоматическому `GITHUB_TOKEN` (настраивать нечего).
2. Сборка двух образов параллельно (matrix: backend, frontend).
3. Push с двумя тегами:

```
ghcr.io/raznaz/estimator-backend:<sha>     ← точная версия, для отката
ghcr.io/raznaz/estimator-backend:latest
ghcr.io/raznaz/estimator-frontend:<sha>
ghcr.io/raznaz/estimator-frontend:latest
```

Первая сборка 3–5 мин, дальше `cache-from: type=gha` → около минуты,
если менялся только код, а не `package.json`.

### 3в. `deploy.yml`, job `deploy`

Условие включения:

```yaml
if: vars.DEPLOY_ENABLED == 'true'
```

**Пока переменной нет** — job серый, «Skipped», workflow при этом зелёный.
Образы собираются и ждут сервера.

**После настройки сервера** выполняется по SSH под пользователем `deploy`:

```
sed -i "IMAGE_TAG=<sha>" .env.prod          фиксируем версию
docker compose pull                          тянем образы из GHCR (~20 сек)
docker compose run --rm backend \
  npx prisma migrate deploy                  МИГРАЦИИ — до перезапуска
docker compose up -d                         пересоздаёт изменившиеся контейнеры
docker image prune -f                        чистим старые образы
```

Затем отдельный шаг **проверяет, что прод жив**: до 12 попыток с интервалом
5 сек на `https://api.<домен>/health`, потом запрос к фронту. Не ответило за
минуту → job красный.

Весь деплой — **1–2 минуты**.

## Что видит пользователь сайта во время деплоя

- Открытые страницы не ломаются — загруженный JS работает.
- **WebSocket рвётся** на момент перезапуска бэкенда; Socket.IO переподключается
  сам через пару секунд, состояние комнаты на это время замирает.
- Зашедший ровно в эти ~5 секунд увидит ошибку Caddy.

Zero-downtime (новая версия рядом со старой) на одном VPS усложняет схему
непропорционально выигрышу — не делаем.

## Разбор первого реального прогона (02.08.2026)

Первый push в `main` — прогоны
[CI 30755466177](https://github.com/Raznaz/estimator-v1/actions/runs/30755466177)
и [Deploy 30755466141](https://github.com/Raznaz/estimator-v1/actions/runs/30755466141).

**CI — зелёный, 1 мин 5 сек.** Все шаги прошли: линт (4 warning, 0 errors),
typecheck, 27 тестов, сборка. Ровно как на локальной имитации.

**Deploy — упал за 23 сек**, оба образа:

```
ERROR: failed to build: invalid tag
"ghcr.io/Raznaz/estimator-backend:1695b6a…": repository name must be lowercase
```

Причина: `${{ github.repository_owner }}` возвращает имя **как оно записано
в GitHub** — `Raznaz` с заглавной. Docker требует имя репозитория строчными.

Починка — шаг, приводящий имя к нижнему регистру перед сборкой:

```yaml
- name: Имя владельца строчными буквами
  id: owner
  run: |
    lc=$(echo "$GITHUB_REPOSITORY_OWNER" | tr '[:upper:]' '[:lower:]')
    echo "lc=$lc" >> "$GITHUB_OUTPUT"
```

Дальше в тегах используется `${{ steps.owner.outputs.lc }}`.
`tr` вместо bash-раскрытия `${VAR,,}` — не зависит от версии оболочки.

Заодно в `docker-compose.prod.yml` был неверный владелец в дефолтах образов
(`nazraz` вместо `raznaz`) — исправлено.

**Второй урок из того же прогона:** matrix-сборка по умолчанию отменяет
оставшиеся варианты при падении одного (`The strategy configuration was
canceled because "build.frontend" failed`). Здесь это было кстати — обе
сборки падали по одной причине.

**Третий:** GitHub предупредил, что actions работают на устаревшем Node 20.
Версии в проекте отстали на несколько мажорных — обновлены до
`checkout@v7`, `setup-node@v7`, `setup-buildx-action@v4`,
`login-action@v4`, `build-push-action@v7`.

## Где и сколько хранятся образы

**Где:** GitHub Container Registry (`ghcr.io`), привязка к аккаунту, а не
к репозиторию → <https://github.com/Raznaz?tab=packages>

**Сколько весят.** В реестре образы лежат сжатыми, примерно втрое меньше,
чем показывает локальный `docker images`:

| Образ | Распакованный | В реестре (оценка) |
|---|---|---|
| `estimator-backend` | 831 МБ | ~300 МБ |
| `estimator-frontend` | 279 МБ | ~100 МБ |

Каждый push **не** добавляет полный объём: одинаковые слои хранятся один раз.
Базовый `node:22-alpine` и слой с `node_modules` не меняются, пока не тронут
`package.json`, — обычный деплой добавляет единицы мегабайт (слой с `dist`).

**Как долго.** Бессрочно: GitHub ничего не удаляет сам. Каждый push в `main`
создаёт новую версию с тегом-SHA, они накапливаются. Отдельно — артефакты
`*.dockerbuild` (отчёты buildx), они живут 90 дней и чистятся автоматически.

### Подвох: лимиты приватных пакетов

Пакеты сейчас **приватные**, а приватные считаются в квоту GitHub Packages —
на Free-тарифе это примерно 500 МБ хранилища и 1 ГБ исходящего трафика в месяц.
Первая пара образов почти выбирает хранилище, а каждый `docker compose pull`
на сервере тянет ~400 МБ → двух-трёх деплоев хватает на месячный трафик.

Точные цифры смотреть в **Settings → Billing and licensing → Plans and usage**,
строка Packages.

### Варианты решения (отложено 02.08.2026)

1. **Сделать пакеты публичными** — для публичных образов GHCR не берёт ни за
   хранение, ни за трафик. Секретов в образах нет: `.env` в `.dockerignore`,
   `DATABASE_URL`/JWT приходят из окружения на сервере. Видно станет только
   скомпилированный `dist` и бандл фронта. Package settings → Change visibility.
2. **Автоочистка старых версий** — job, оставляющий 3–5 последних. Нужен
   в любом случае, чтобы список версий не разросся.
3. **Ужать backend-образ** — 831 МБ из-за dev-зависимостей, оставленных ради
   Prisma CLI для миграций. Вынести миграции отдельно → примерно вдвое меньше.

**Текущее решение:** оставляем приватными, возвращаемся к вопросу при упоре
в лимиты.

## Известный изъян: `deploy.yml` не ждёт `ci.yml`

Оба стартуют от одного события (push в `main`) и бегут параллельно.
Теоретически образы уедут в реестр раньше, чем CI обнаружит поломку.

Почему сейчас терпимо: при защищённой ветке `main` (этап 8) попасть туда можно
только через PR с зелёным CI, плюс job `deploy` сам проверяет `/health`.

Варианты починки, если понадобится строгость:

- **Простой** — продублировать проверки job'ом в `deploy.yml` с `needs:`.
  Минус: CI выполняется дважды, +2–3 мин к деплою.
- **Правильный** — запускать `deploy.yml` через `workflow_run` по факту
  успешного `ci.yml`. Хитрее в настройке, зато без дублирования.

## Две сводные картинки

**Сегодня (сервера нет):**

```
push в ветку   → ничего
открыл PR      → CI (2–3 мин) → зелёный чек, можно мёржить
мёрж в main    → CI ещё раз + сборка образов в GHCR
                 деплой пропущен (DEPLOY_ENABLED не задан)
```

**После этапа 7:**

```
push в ветку   → ничего
открыл PR      → CI (2–3 мин)
мёрж в main    → CI + сборка образов
                 → SSH на сервер → миграции → up -d
                 → проверка /health
                 → сайт обновлён, ~5 минут от мёржа
```
