# OpenSpec: как это устроено

Разбор для тех, кто впервые видит SDD-процесс в этом репозитории.

## Зачем

До сих пор требования у нас жили в голове и в ad-hoc файлах `.claude/plans/*.md`.
Проблема не в том, что «мало документации», а в том, что **нет момента, когда
зафиксировано, что значит „готово“, — до написания кода**. Ревью идёт по голому
diff: видно *как* сделано, но не видно, *что* вообще должно было получиться.

OpenSpec вставляет ровно один шаг перед кодом: короткий Markdown-документ с
требованиями и сценариями, который проверяет человек. Потом по нему пишется код,
и в PR едут оба — спека и diff.

## Две половины: терминал и чат

Главная путаница новичков. OpenSpec — это две разные вещи с похожими именами.

```
        ТЕРМИНАЛ                              ЧАТ CLAUDE CODE
   ┌──────────────────────┐               ┌──────────────────────────────┐
   │  npx openspec list   │   ставит      │  /opsx:propose добавить …     │
   │  npx openspec view   │  ──────────►  │  /opsx:apply                  │
   │  npx openspec doctor │  команды      │  /opsx:archive                │
   └──────────────────────┘               └──────────────────────────────┘
```

- `npx openspec ...` — **CLI**, программа в терминале. Ставит структуру, валидирует,
  показывает дашборд. Это «движок»: он знает правила — как устроена папка изменения,
  как дельта вливается в основную спеку.
- `/opsx:...` — **slash-команды в чате**. Это «руль»: инструкции агенту следовать
  workflow. Никакого «интерактивного режима» включать не надо — просто набираешь
  `/opsx:propose` в чате, как обычный запрос.

`openspec init` в терминале — это то, что **установило** чатовые команды. Дальше
повседневная работа почти целиком в чате.

Если набрать `/opsx:propose` в терминале — ничего не произойдёт. Это самая частая
ошибка.

## Что где лежит

```
openspec/
├── config.yaml         # контекст проекта и правила, инжектятся в промпт агента
├── specs/              # источник правды: как система себя ВЕДЁТ сейчас
│   └── <домен>/spec.md
└── changes/            # активные изменения, по папке на изменение
    ├── <change-id>/
    │   ├── proposal.md # зачем и что меняем
    │   ├── design.md   # технический подход
    │   ├── tasks.md    # чек-лист реализации
    │   └── specs/      # ДЕЛЬТА: что именно меняется в требованиях
    │       └── <домен>/spec.md
    └── archive/        # завершённые изменения
```

Плюс сгенерированные файлы регистрации команд — их тоже коммитим:
`.claude/skills/openspec-*/SKILL.md` и `.claude/commands/opsx/*.md`.

Ключевое различие: `specs/` — это **состояние**, `changes/*/specs/` — это **дельта**.

## Формат спеки

Обычный Markdown, без спецсинтаксиса:

```markdown
## ADDED Requirements

### Requirement: Список тикетов комнаты
Система SHALL возвращать тикеты комнаты в порядке создания.

#### Scenario: Успешный запрос участником
- **GIVEN** пользователь — участник комнаты
- **WHEN** он запрашивает GET /rooms/:code/tickets
- **THEN** возвращается 200 и массив тикетов в порядке создания

#### Scenario: Запрос без токена
- **WHEN** запрос приходит без Authorization
- **THEN** возвращается 401
```

Правила, которые реально важны:

- **Один requirement — одно наблюдаемое поведение.** Если в формулировке три
  «и ещё», это три требования.
- **Проверяемость.** «Показывать баннер ошибки при загрузке от 10 МБ» — годится.
  «Аккуратно обрабатывать загрузки» — нет.
- **RFC 2119:** `SHALL`/`MUST` — обязательно, `SHOULD` — сильная рекомендация,
  `MAY` — опционально.
- Сценарии покрывают ошибки, а не только happy path.

### Типы дельт

| Тип | Когда |
|---|---|
| `ADDED` | новое поведение |
| `MODIFIED` | меняется существующее — пишем **полную новую версию** требования |
| `REMOVED` | поведение удаляется — с указанием причины |

Перепутать типы — значит получить в архиве конкурирующие или осиротевшие
требования. Это единственная вещь, где легко сделать больно.

## Цикл

```
git switch -c spec/<что-делаем>
   ↓
/opsx:explore <тема>     — необязательно; агент читает код, обсуждаем идею
   ↓
/opsx:propose <описание> — создаётся changes/<id>/ со всеми артефактами
   ↓
   ЧЕЛОВЕК ЧИТАЕТ И ПРАВИТ  ← вот ради этого шага всё и затевалось
   /opsx:update — если нужно переписать план
   npx openspec validate --all --strict
   ↓
/opsx:apply              — агент реализует tasks.md
   ↓
коммит + PR: спека и код едут вместе
   ↓
после мерджа: /opsx:archive — дельта вливается в specs/, изменение в archive/
```

Полный список команд профиля `core` (у нас включён он):
`explore`, `propose`, `update`, `apply`, `sync`, `archive`.
`sync` — влить дельту в основные спеки **без** архивации, нужен редко.

## Что важно понимать про brownfield

**Мы не документируем существующий код.** Это не «сначала опишем всё, потом
начнём» — так подход умирает на второй неделе. Спека пишется только на то, что
прямо сейчас меняешь. `openspec/specs/` наполняется естественно: через год там
будет описано ровно то, что за год трогали.

Старые доки (`.claude/plans/auth-cqrs.md` и прочее) остаются как справочный
материал. Мы их не конвертируем.

## Когда спека не нужна

- багфикс, не меняющий заявленное поведение;
- рефакторинг без изменения контракта;
- правки конфигов, CI, зависимостей.

Спека нужна, когда меняется **наблюдаемое поведение системы**.

## Git

OpenSpec **никогда не трогает git** — только читает и пишет Markdown. Ветками,
коммитами и PR управляем сами. Одно изменение — один автор (одна папка в
`changes/`), поэтому конфликты между людьми почти не возникают.

Архивировать — **после** мерджа PR, чтобы `specs/` отражала только реально
уехавший в main код.

## Шпаргалка

```bash
npm run spec:list         # активные изменения
npm run spec:validate     # структурная проверка (это же гоняет CI)
npm run spec:view         # интерактивный дашборд
npx openspec doctor       # здоровье установки
npx openspec update       # перегенерировать команды после апгрейда CLI
```

Если `/opsx` перестал автодополняться в чате: `npx openspec update` и перезапуск
Claude Code.
