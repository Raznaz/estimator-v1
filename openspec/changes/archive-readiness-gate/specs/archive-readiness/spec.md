## Purpose

Проверка полноты артефактов изменения перед архивацией: гарантирует, что каждая
объявленная capability имеет спецификацию и покрыта задачами, чтобы при
архивации эпика ни одно согласованное требование не потерялось.

## ADDED Requirements

### Requirement: Каждая объявленная capability имеет спецификацию

Проверка SHALL сообщать об ошибке `missing-spec` для каждой capability,
объявленной в секции `## Capabilities` файла `proposal.md`, для которой в
изменении отсутствует файл спецификации.

Учитываются capability из обоих подразделов — новые и изменяемые.

#### Scenario: Эпик с недостающей спекой

- **GIVEN** изменение объявляет capability `tickets` и `tickets-import`
- **AND** файл спецификации существует только для `tickets`
- **WHEN** выполняется проверка готовности
- **THEN** сообщается ошибка `missing-spec` с именем `tickets-import`
- **AND** код выхода — `1`

#### Scenario: Все объявленные capability обеспечены спеками

- **GIVEN** изменение объявляет capability `tickets` и `tickets-import`
- **AND** для каждой существует файл спецификации
- **WHEN** выполняется проверка готовности
- **THEN** ошибок не сообщается и код выхода — `0`

#### Scenario: Изменяемая capability учитывается наравне с новой

- **GIVEN** изменение объявляет `tickets` в подразделе изменяемых capability
- **AND** файл спецификации для `tickets` в изменении отсутствует
- **WHEN** выполняется проверка готовности
- **THEN** сообщается ошибка `missing-spec` с именем `tickets`

#### Scenario: Плейсхолдеры шаблона не считаются capability

- **GIVEN** секция `## Capabilities` содержит незаполненные плейсхолдеры
  шаблона вместо реальных имён
- **WHEN** выполняется проверка готовности
- **THEN** плейсхолдеры не порождают ошибок `missing-spec`

#### Scenario: Формулировка об отсутствии изменяемых capability

- **GIVEN** подраздел изменяемых capability содержит текст «Нет.» без имён
- **WHEN** выполняется проверка готовности
- **THEN** этот текст не интерпретируется как имя capability

### Requirement: Спецификации без объявления отклоняются

Проверка SHALL сообщать об ошибке `undeclared-spec` для каждого файла
спецификации, чья capability не объявлена в `proposal.md`.

Требование ловит опечатки в имени папки, из-за которых спецификация при
архивации вливается не в ту capability или создаёт постороннюю.

#### Scenario: Опечатка в имени папки capability

- **GIVEN** изменение объявляет capability `tickets`
- **AND** файл спецификации лежит в папке с именем `tikets`
- **WHEN** выполняется проверка готовности
- **THEN** сообщается ошибка `undeclared-spec` с именем `tikets`
- **AND** дополнительно сообщается ошибка `missing-spec` с именем `tickets`
- **AND** код выхода — `1`

### Requirement: Каждая capability эпика покрыта задачами

Если изменение объявляет более одной capability, проверка SHALL требовать, чтобы
в `tasks.md` для каждой capability существовала хотя бы одна группа задач,
помеченная именем этой capability в заголовке.

Capability без единой группы SHALL давать ошибку `uncovered-capability`.
Пометка на группе, не соответствующая ни одной объявленной capability, SHALL
давать ошибку `unknown-capability-tag`.

При единственной объявленной capability пометки не требуются: все задачи
считаются относящимися к ней.

#### Scenario: Capability без задач

- **GIVEN** изменение объявляет `tickets` и `tickets-import`, обе имеют спеки
- **AND** в `tasks.md` помечены группы только для `tickets`
- **WHEN** выполняется проверка готовности
- **THEN** сообщается ошибка `uncovered-capability` с именем `tickets-import`
- **AND** код выхода — `1`

#### Scenario: Пометка на несуществующую capability

- **GIVEN** изменение объявляет `tickets` и `tickets-import`
- **AND** в `tasks.md` есть группа, помеченная именем `tickets-export`
- **WHEN** выполняется проверка готовности
- **THEN** сообщается ошибка `unknown-capability-tag` с именем `tickets-export`

#### Scenario: Единственная capability не требует пометок

- **GIVEN** изменение объявляет ровно одну capability и имеет для неё спеку
- **AND** ни одна группа задач в `tasks.md` не помечена именем capability
- **WHEN** выполняется проверка готовности
- **THEN** ошибок покрытия не сообщается и код выхода — `0`

#### Scenario: Эпик с полным покрытием

- **GIVEN** изменение объявляет `tickets` и `tickets-import`
- **AND** обе имеют спеки и хотя бы по одной помеченной группе задач
- **WHEN** выполняется проверка готовности
- **THEN** ошибок не сообщается и код выхода — `0`

### Requirement: Область проверки и код выхода

Проверка SHALL по умолчанию охватывать все активные изменения и SHALL
ограничиваться одним изменением, если оно указано явно. Архив завершённых
изменений проверке не подлежит.

Код выхода SHALL быть `0`, когда ошибок не обнаружено, и `1`, когда обнаружена
хотя бы одна ошибка в любом из проверяемых изменений.

#### Scenario: Проверка всех активных изменений

- **GIVEN** есть два активных изменения, одно из которых содержит ошибку
- **WHEN** проверка запускается без указания изменения
- **THEN** в отчёте присутствуют оба изменения
- **AND** код выхода — `1`

#### Scenario: Проверка одного изменения

- **GIVEN** есть два активных изменения, ошибка только во втором
- **WHEN** проверка запускается с указанием первого изменения
- **THEN** отчёт содержит только первое изменение и код выхода — `0`

#### Scenario: Архивные изменения не проверяются

- **GIVEN** в архиве лежит завершённое изменение с недостающей спекой
- **WHEN** проверка запускается без указания изменения
- **THEN** архивное изменение в отчёте отсутствует и на код выхода не влияет

#### Scenario: Указано несуществующее изменение

- **WHEN** проверка запускается с именем изменения, которого нет
- **THEN** сообщается об ошибке и код выхода — `1`

#### Scenario: Активных изменений нет

- **GIVEN** ни одного активного изменения не существует
- **WHEN** выполняется проверка готовности
- **THEN** проверка завершается успешно с кодом выхода `0`

### Requirement: Пропуск изменений без спецификаций

Проверка SHALL пропускать изменение, которое явно отказалось от спецификаций,
и SHALL отражать факт пропуска в отчёте.

#### Scenario: Изменение с отказом от спек

- **GIVEN** изменение помечено как не требующее спецификаций
- **AND** секция `## Capabilities` в нём не заполнена
- **WHEN** выполняется проверка готовности
- **THEN** изменение отмечается как пропущенное
- **AND** ошибок по нему не сообщается и код выхода — `0`

### Requirement: Машиночитаемый отчёт

Проверка SHALL поддерживать вывод результата в машиночитаемом формате, в котором
для каждого проверяемого изменения перечислены его ошибки с кодом и именем
capability.

Код выхода в машиночитаемом режиме SHALL совпадать с кодом выхода обычного
режима при тех же входных данных.

#### Scenario: Машиночитаемый вывод при ошибке

- **GIVEN** изменение содержит недостающую спеку
- **WHEN** проверка запускается в машиночитаемом режиме
- **THEN** вывод поддаётся разбору как структурированные данные
- **AND** содержит имя изменения, код ошибки `missing-spec` и имя capability
- **AND** код выхода — `1`

#### Scenario: Машиночитаемый вывод при успехе

- **GIVEN** все проверяемые изменения корректны
- **WHEN** проверка запускается в машиночитаемом режиме
- **THEN** вывод поддаётся разбору и содержит пустой список ошибок
- **AND** код выхода — `0`
