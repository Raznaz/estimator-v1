# Design: Гейт готовности изменения к архивации

## Context

Мотивация — см. `proposal.md` → Why. Требования — см.
`specs/archive-readiness/spec.md`.

Разбор `node_modules/@fission-ai/openspec/dist` показал, где именно проходит
граница встроенных проверок:

| Механизм | Файл | Что делает |
|---|---|---|
| Завершённость артефакта | `core/artifact-graph/outputs.js:37` | `resolveArtifactOutputs(...).length > 0` — одного файла хватает для glob-артефакта |
| Валидатор | `core/validation/validator.js` | Структура дельт: SHALL/MUST, ≥1 сценарий, дубли, коллизии секций. Секцию `## Capabilities` не читает |
| Архивация | `core/archive.js:317-342` | Считает незакрытые `- [ ]`; при `--yes` — только предупреждение |

Ни один из трёх не связывает объявленные capability с фактическими спеками.
Раскладка `specs/<area>/<capability>/spec.md` поддерживается (`core/specs-apply.js:26`),
то есть путь capability может быть вложенным.

## Goals / Non-Goals

**Goals**

- Работать без сети и без запуска OpenSpec CLI: гейт должен быть дешёвым, чтобы
  висеть в CI на каждом PR.
- Никаких новых зависимостей: репозиторий и так тянет два фреймворка.
- Логика, тестируемая без файловой системы там, где это возможно.

**Non-Goals**

- Не заменяем `openspec validate` — гейт дополняет его, а не дублирует.
- Не встраиваемся в `openspec archive`: пакет обновляется, патчить его поведение
  означало бы ломаться на каждом апгрейде.
- Не пытаемся понять смысл требований — только структурная полнота.

## Decisions

### 1. Отдельный Node-скрипт, а не кастомная схема OpenSpec

OpenSpec позволяет форкнуть схему (`openspec schema fork`) и добавить свой
артефакт с собственными правилами. Соблазнительно, но не решает задачу: схема
управляет тем, какие артефакты создаются и в каком порядке, а не тем, полон ли
их набор относительно `proposal.md`. Валидация схемы проверяет структуру
шаблонов, а не перекрёстные ссылки между артефактами.

Отдельный скрипт даёт ровно нужное и переживает апгрейды пакета.

*Альтернативы:* патч поведения `archive` в `node_modules` — отклонено,
ломается при каждом обновлении. Кастомная схема — отклонено, не тот уровень.

### 2. Список изменений — из файловой системы, а не из `openspec list --json`

Гейт обходит `openspec/changes/*/`, пропуская `archive/`. Папка считается
изменением, если содержит `.openspec.yaml` — этот файл создаёт
`openspec new change`, и он же хранит маркер `skip_specs`.

Вызов CLI подпроцессом дал бы формально более «правильный» источник, но добавил
бы ~секунду на запуск, зависимость от установленного пакета в CI и сложность в
тестах. Парсить `proposal.md` и `tasks.md` всё равно приходится напрямую с
диска, так что согласованности от подпроцесса не прибавится.

*Риск:* смена раскладки папок в будущей мажорной версии OpenSpec сломает гейт.
Принимаем: поломка будет громкой (гейт упадёт), а не тихой.

### 3. Разметка capability — inline-код в заголовке группы задач

```markdown
## 4. Импорт из JIRA — `tickets-import`
```

Из заголовка `##` извлекается содержимое обратных кавычек и сверяется с набором
объявленных capability.

Почему так:
- согласуется с тем, как capability уже записываются в `proposal.md` —
  тем же inline-кодом;
- не требует нового синтаксиса, невидимых HTML-комментариев или отдельного файла
  трассировки;
- заголовок остаётся читаемым человеком и в GitHub-рендере.

Разметка обязательна только при более чем одной capability. Это сохраняет
дешевизну обычных изменений (их большинство) и не требует правки уже
написанного `tickets-rest-api/tasks.md`.

*Альтернативы:* маркер в тексте каждой задачи — шумно и многословно; отдельный
файл трассировки — ещё один артефакт, который разъедется с реальностью;
эвристика «упоминание имени capability где угодно в задаче» — даёт ложные
срабатывания на общих словах.

### 4. Разбор Markdown — целевой, без библиотеки

Полноценный парсер не нужен: достаточно построчного разбора двух узких мест —
пунктов списка под `### New Capabilities` / `### Modified Capabilities` и
заголовков `##` в `tasks.md`.

Отбрасываются:
- плейсхолдеры шаблона (`<name>`, `<existing-name>`) — угловые скобки;
- пункты без inline-кода (наш `proposal.md` пишет в изменяемых просто «Нет.»);
- всё, что не kebab-case.

Маркер `skip_specs` читается регулярным выражением по `.openspec.yaml`, а не
YAML-парсером: нужно ровно одно булево поле, тянуть парсер ради него избыточно.

### 5. Отсутствие `proposal.md` трактуется как «нет объявленных capability»

Если файла нет, набор объявленных capability пуст. Любая существующая спека
тогда даст `undeclared-spec` — сигнал появится, а не потеряется. Отдельного кода
ошибки на этот случай не вводим: незавершённость артефактов и так видна в
`openspec status`.

### 6. Структура кода — чистое ядро и тонкая оболочка

Разбор proposal, сбор спек, разбор заголовков задач и сверка — чистые функции,
принимающие строки и возвращающие результат. Работа с диском и `process.exit` —
отдельный слой. Так основная масса кейсов из спеки тестируется на строках, а
файловые фикстуры нужны лишь для обхода папок.

Коды ошибок (`missing-spec`, `undeclared-spec`, `uncovered-capability`,
`unknown-capability-tag`) — часть наблюдаемого контракта, зафиксированного в
спеке, и используются как в человекочитаемом, так и в машиночитаемом выводе.

## Risks / Trade-offs

- **Разметка capability — новое ручное соглашение, о нём забудут.** → Правило
  уходит в `rules.tasks` в `openspec/config.yaml`, поэтому агент проставляет её
  сам при генерации `tasks.md`; забывчивость ловит сам гейт в CI.
- **Гейт знает о внутренней раскладке OpenSpec.** → Ограничено двумя фактами:
  папка `openspec/changes/` и файл `.openspec.yaml`. Оба стабильны с 1.x.
- **Проверка структурная, а не содержательная**: спека может существовать и быть
  пустой заглушкой. → Осознанно: содержательная проверка — это `/opsx:verify` из
  профиля `workflows`, вне скоупа.
- **Вложенные capability** (`specs/<area>/<capability>/`) поддерживаются, но
  требуют объявления полного пути в `proposal.md`. → Поддерживаем, не
  рекомендуем; в документации остаётся плоская раскладка.

## Migration Plan

Изменение аддитивное: новые файлы плюс шаги в CI. Существующий
`tickets-rest-api` объявляет одну capability и проходит гейт без правок.
Откат — обычный откат коммита; на процесс работы с OpenSpec это не влияет.
