# Proposal: Гейт готовности изменения к архивации

## Why

Артефакт `specs` в OpenSpec — glob (`specs/**/*.md`), а его завершённость
определяется как «найден хотя бы один файл»
(`core/artifact-graph/outputs.js:37`). Секцию `## Capabilities` из
`proposal.md` не читает ни `status`, ни валидатор.

Пока в изменении одна capability, это незаметно. Но как только изменение
становится эпиком с несколькими спеками, появляется тихий провал: proposal
объявляет четыре capability, автор написал одну спеку — `openspec status`
рапортует «All artifacts complete», `openspec validate --strict` проходит,
`openspec archive` отрабатывает и вливает в `openspec/specs/` одну спеку из
четырёх. Требования трёх остальных capability исчезают без единого
предупреждения, а изменение уже уехало в архив.

Ошибка обнаруживается спустя недели — когда кто-то ищет в `openspec/specs/`
поведение, которое было согласовано и реализовано, но не сохранено.

## What Changes

- **Добавляется** проверка готовности изменения к архивации, доступная как
  команда командной строки и как шаг CI.
- **Добавляется** сверка объявленных в `proposal.md` capability с фактическими
  файлами спек — в обе стороны: заявленная без файла и файл без объявления.
- **Добавляется** проверка покрытия: у каждой capability эпика есть хотя бы
  одна группа задач в `tasks.md`.
- **Добавляется** соглашение о разметке: при более чем одной capability группа
  задач помечает свою capability inline-кодом в заголовке. Правило закрепляется
  в `openspec/config.yaml`, чтобы агент проставлял разметку при генерации.
- Изменения с `skip_specs: true` проверка пропускает: спек у них нет по
  определению.

Ломающих изменений нет: существующий `tickets-rest-api` объявляет одну
capability и проходит проверку без правок.

### Вне скоупа

- **Проверка незакрытых задач.** Её делает встроенный `openspec archive`
  (`core/archive.js:317-342`). Известное ограничение: флаг `--yes` низводит
  блокировку до предупреждения. Ужесточение — отдельным изменением.
- **Проверка соответствия реализации спеке.** Это `/opsx:verify` из профиля
  `workflows`; проект на профиле `core`, переключение сюда не входит.
- Автоматический запуск перед `openspec archive` — гейт вызывается явно
  и работает в CI, в сам процесс архивации не встраивается.

## Capabilities

### New Capabilities

- `archive-readiness`: проверка полноты артефактов изменения перед архивацией —
  сверка capability со спеками, покрытие capability задачами, коды выхода и
  состав отчёта.

### Modified Capabilities

Нет. Единственная существующая спека — `tickets` — не затрагивается.

## Impact

**Новый код:**

- `scripts/spec-readiness.mjs` — сам гейт. Чистый Node (ESM), без новых
  зависимостей. Папки `scripts/` в корне пока нет.
- `scripts/spec-readiness.test.mjs` — тесты на встроенном `node --test`.

**Изменяется:**

- `package.json` (корень) — скрипты `spec:ready` и `spec:ready:test`.
- `.github/workflows/ci.yml` — шаги проверки спек.
- `openspec/config.yaml` — правило разметки capability в `rules.tasks`.
- `.claude/docs/openspec-workflow.md` — раздел про эпики и гейт.

**Не затрагивается:** код приложения (`backend/`, `frontend/`), схема Prisma,
shared-контракт. Изменение целиком в тулинге процесса.
