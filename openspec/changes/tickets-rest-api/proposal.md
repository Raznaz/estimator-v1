# Proposal: REST-эндпоинты управления тикетами комнаты

## Why

Тикетами сейчас можно управлять только из активной socket-сессии: единственный
способ создать тикет — событие `CREATE_TICKET` в
`backend/src/poker/poker.gateway.ts`. Модуль `tickets` при этом существует,
но его контроллер пуст и содержит три TODO — REST-доступа к тикетам нет вовсе.

Из-за этого невозможны сценарии вне живой сессии: подготовить список тикетов
до начала refinement, посмотреть очередь комнаты, зафиксировать итоговую оценку
после обсуждения. Поле `Ticket.finalEstimate` заведено в схеме Prisma, но не
заполняется никаким кодом — финальную оценку сохранить сегодня нечем.

## What Changes

- **Добавляется** `POST /tickets` — создание тикета в комнате. Тело: `roomId`,
  необязательный `title`. Доступно только владельцу комнаты.
- **Добавляется** `GET /tickets?roomId=` — список тикетов комнаты в порядке
  очереди (`order` по возрастанию). Доступен любому участнику комнаты.
- **Добавляется** `PATCH /tickets/:id/estimate` — фиксация финальной оценки:
  заполняет `finalEstimate` и переводит `status` в `ESTIMATED`. Доступно только
  владельцу комнаты.
- **Добавляется** рассылка `ROOM_STATE` в комнату после REST-мутаций (`POST` и
  `PATCH`), чтобы подключённые по socket клиенты видели изменения немедленно.
  Без этого REST-путь разошёлся бы с socket-путём и нарушил главный инвариант
  продукта — синхронность состояния у всех участников.
- Значение финальной оценки **валидируется по шкале комнаты** (`Room.scaleType`,
  `backend/src/shared/scales.ts`) — произвольную строку записать нельзя.
- Модель прав повторяет socket-путь: мутации — только владелец комнаты
  (сегодня это `assertOwner` в `poker.service.ts`), иначе `403`.

Ломающих изменений нет: добавляются только новые эндпоинты.

### Вне скоупа

- Socket-хендлер `CREATE_TICKET` остаётся как есть. Дублирование REST- и
  socket-путей создания тикета в этом изменении **не устраняется**.
- Редактирование и удаление тикетов, изменение порядка (`order`), поля
  `externalKey` и `description` — не трогаем.
- Статусы `SKIPPED` и возврат тикета из `ESTIMATED` обратно в работу.
- Клиентская часть: frontend REST-эндпоинты пока не использует.

## Capabilities

### New Capabilities

- `tickets`: управление тикетами комнаты через REST — создание, чтение очереди,
  фиксация финальной оценки, права доступа и синхронизация с socket-состоянием.

### Modified Capabilities

Нет. `openspec/specs/` пока пуст, существующих спек, чьи требования менялись бы,
не существует.

## Impact

**Затрагиваемый код (backend):**

- `backend/src/tickets/tickets.controller.ts` — три новых эндпоинта, Swagger.
- `backend/src/tickets/tickets.service.ts` — переиспользуются существующие
  `create()` и `listByRoom()`; добавляется метод фиксации оценки и проверки прав.
- `backend/src/tickets/dto/` и `dto/responses/` — новые DTO запросов и моделей
  ответов.
- `backend/src/tickets/tickets.module.ts` — зависимости для проверки прав и
  рассылки состояния.
- `backend/src/main.ts` — тег `tickets` в `DocumentBuilder`.

**Не затрагивается:**

- Схема Prisma — `finalEstimate`, `status` и `order` уже есть, миграция не нужна.
- shared-контракт (`events.ts` / `types.ts` / `scales.ts`) в обеих копиях: тип
  `Ticket` уже содержит `finalEstimate`, новых socket-событий не вводится.
  REST-DTO живут в `backend/src/tickets/dto/` и в контракт не попадают.
- Модуль остаётся на обычном сервисе, без перевода на CQRS.

**Риск, разбираемый в design.md:** рассылка `ROOM_STATE` из REST требует доступа
к `PokerGateway`/`PokerService` из модуля `tickets`, а `poker` уже зависит от
`tickets` — возможен циклический импорт модулей. Способ развязки выбирается в
design.
