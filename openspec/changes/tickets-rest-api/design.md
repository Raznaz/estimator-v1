# Design: REST-эндпоинты управления тикетами комнаты

## Context

Мотивация — см. `proposal.md` → Why. Требования — см. `specs/tickets/spec.md`.

Технические ограничения, определяющие подход:

1. **`PokerModule` уже импортирует `TicketsModule`**
   (`backend/src/poker/poker.module.ts`). Прямая обратная зависимость
   `tickets → poker`, нужная для рассылки `ROOM_STATE`, даст цикл модулей.
2. **Проверка «владелец комнаты» сейчас живёт приватным методом `assertOwner`**
   в `backend/src/poker/poker.service.ts` и наружу не экспортируется.
3. **Рассылка состояния завязана на socket**: `PokerService.buildRoomState(roomCode)`
   строит состояние, а рассылает его `PokerGateway` через `server.to(roomCode)`.
   Доступ к `server` есть только у gateway.
4. **`CqrsModule` уже подключён** в `poker`, `rooms`, `auth`, `users`, но
   используется только `CommandBus`/`QueryBus` — `EventBus` в проекте пока не
   применяется ни разу.
5. **Шкалы** лежат в `backend/src/shared/scales.ts`: `SCALES: Record<ScaleType,
   readonly string[]>` и `SPECIAL_CARDS` (`?`, `☕`). Это дублируемый контракт —
   менять его нельзя.

## Goals / Non-Goals

**Goals**

- Развязать `tickets` и `poker` так, чтобы REST-мутации доходили до socket-клиентов
  без циклической зависимости модулей.
- Оставить `tickets` framework-agnostic по отношению к socket: модуль не должен
  знать ни про `Server`, ни про `ROOM_STATE`.

**Non-Goals**

- Не вводим гарантию доставки: рассылка — best-effort, как и на socket-пути.
- Не консолидируем проверку прав между `poker` и `tickets` в общий модуль.
- Не переводим `tickets` на CQRS-хендлеры: команды/запросы остаются методами
  сервиса, `EventBus` используется только как шина событий.

## Decisions

### 1. Рассылка состояния — через `EventBus`, а не прямой вызов gateway

`TicketsService` после успешной мутации публикует доменное событие
(`RoomTicketsChangedEvent` с `roomCode`) в `EventBus`. В модуле `poker`
появляется `@EventsHandler(RoomTicketsChangedEvent)`, который инжектит
`PokerGateway`, зовёт `buildRoomState(roomCode)` и рассылает `ROOM_STATE`
в комнату.

Направление зависимости получается `poker → tickets` — то же, что уже есть.
Цикла нет: `tickets` зависит только от `CqrsModule`, о существовании `poker`
не знает.

*Альтернативы:*

- **`forwardRef(() => PokerModule)`** — работает, но узаконивает цикл: любая
  последующая правка любого из двух модулей рискует уронить порядок
  инициализации. Отклонено.
- **Перенести REST-контроллер тикетов в `PokerModule`** — снимает проблему, но
  размывает границу модулей: REST тикетов оказался бы в модуле real-time.
  Отклонено.
- **Не рассылать вовсе** — отклонено на уровне спеки: требование
  «Синхронизация REST-изменений с участниками комнаты» существует именно
  потому, что расхождение REST- и socket-путей ломает главный инвариант
  продукта.

Событие несёт `roomCode`, а не `roomId`: `buildRoomState` принимает код, а
`TicketsService` всё равно загружает комнату при проверке прав, так что код у
него на руках.

### 2. Проверка прав — своя, внутри `TicketsService`

`TicketsService` получает приватный метод, загружающий комнату по `roomId` и
сверяющий `room.ownerId` с `userId`: `NotFoundException` если комнаты нет,
`ForbiddenException` если пользователь не владелец. Логика повторяет
`assertOwner` из `PokerService`.

Это осознанный дубль двух проверок примерно на пять строк. Вынести общий
`assertOwner` в `RoomsService` было бы чище, но потребовало бы править
`poker.service.ts` и его тесты — то есть расширить скоуп изменения ради
рефакторинга. Дубль зафиксирован здесь как известный долг.

`GET` списка прав владельца не требует — по спеке очередь доступна любому
участнику. Проверяется только аутентификация и существование комнаты.

### 3. Валидация оценки — по шкале комнаты, спецкарты отклоняются

Валидировать значение в DTO нельзя: допустимое множество зависит от
`Room.scaleType`, то есть от данных. Поэтому проверка живёт в сервисе, после
загрузки комнаты: значение должно входить в `SCALES[room.scaleType]` и не
совпадать ни с одной из `SPECIAL_CARDS`. Иначе `BadRequestException`.

`?` и `☕` входят в шкалу как карты для голосования, но означают «не знаю» и
«нужен перерыв» — финальной оценкой они быть не могут, поэтому исключаются
отдельной проверкой, а не через шкалу.

### 4. Форма эндпоинтов

Сохраняем ровно то, что заявлено в TODO контроллера:

| Метод | Путь | Права | Тело / параметры |
|---|---|---|---|
| `POST` | `/tickets` | владелец | `{ roomId, title? }` |
| `GET` | `/tickets?roomId=` | участник | query `roomId` (обязателен) |
| `PATCH` | `/tickets/:id/estimate` | владелец | `{ value }` |

`roomId` у `GET` — обязательный query-параметр; его отсутствие даёт `400`
(требование спеки «Комната не указана»). Валидация — через `class-validator`
на DTO, `@ApiProperty` руками не проставляем (работает CLI-плагин Nest).

Все три эндпоинта — за `JwtAuthGuard`, `userId` берётся из `@CurrentUser`.
Гостевой доступ работает: гости получают полноценные токены при создании
комнаты и входе (см. `rooms.controller.ts`).

## Risks / Trade-offs

- **`EventBus` — новый для проекта паттерн.** → Применяется точечно, в одном
  месте, поверх уже подключённого `CqrsModule`. Новых зависимостей нет.
- **Рассылка не транзакционна: мутация в БД прошла, рассылка упала.** →
  Считаем допустимым. Socket-путь ведёт себя так же, а следующий `ROOM_STATE`
  (любое действие в комнате) выправит состояние у клиентов.
- **Дубль проверки владельца в двух сервисах.** → Зафиксирован в решении 2 как
  осознанный долг; консолидация — отдельным изменением.
- **REST и socket остаются двумя путями создания тикета** с разным побочным
  эффектом: socket-путь дополнительно открывает голосование
  (`selectTicket`), REST — нет. → Явно вне скоупа (см. `proposal.md`);
  REST создаёт тикет в `PENDING` и очередь не переключает.

## Migration Plan

Миграция не требуется: схема Prisma не меняется, поля `finalEstimate`, `status`
и `order` уже существуют. Изменение аддитивное — добавляются только новые
эндпоинты, существующее поведение не затрагивается. Откат — обычный откат
коммита.
